# Aurora 公考岗位助手需求规格

## 1. 产品定义

Aurora 是面向中国大陆公务员、事业单位招聘的岗位决策助手。它根据用户明确提供的个人条件，检索公开招考公告，筛出可报岗位，基于可核验的历史数据做比较，并给出与目标岗位匹配的备考建议。

Aurora 是信息整理和决策支持工具，不代替招录机关解释政策，不承诺进面或录用结果。任何结论都必须能追溯到公告、官方统计或明确标注为推断。

## 2. MVP 范围

首个版本聚焦江苏省，只支持：

- 用户主动指定的 **一个考试类型**（国考、省考或事业单位）和江苏省范围，可细化到南京、无锡、徐州、常州、苏州、南通、连云港、淮安、盐城、扬州、镇江、泰州、宿迁；
- 从已登记的官方公开来源读取公告、职位表和考试大纲；
- 从江苏 13 个地级市的公办高等专科学校/高职院校官网招聘栏目读取教师、辅导员、实验员和行政岗位信息；
- 对职位表中的硬性条件做结构化筛选；
- 对用户提供或系统已收录的历史分数/报名数据进行对比；
- 输出带来源、更新时间和置信度的岗位清单、分析报告和备考计划。

首个版本不做：自动报名、代替用户联系招录单位、抓取需要登录或绕过验证码的页面、预测具体录取结果、全网无限爬取、收集或推断敏感个人信息。其他省份暂不纳入首版来源白名单。

公办大专范围以人工维护的院校名录为准，不能根据“学院”“职业技术”等名称自动推断公办属性。学校官网是岗位事实的一手来源；第三方招聘平台和培训机构页面只可作为发现线索，不能作为资格或岗位结论依据。

## 3. 用户输入

用户可以通过表单或自然语言提供以下字段；缺失字段必须先询问，不能擅自假设：

| 字段 | 要求 |
| --- | --- |
| 考试类型/年份/省份 | 必填；年份默认当前正在报名的年份，但需向用户确认 |
| 目标地区 | 省、市、区县或“可接受通勤范围” |
| 学历、学位、专业 | 必填；保存原始专业名称及标准化匹配结果 |
| 应届身份、基层经历、政治面貌 | 按公告口径填写，可为未知 |
| 证书、工作年限、户籍、性别等限制 | 仅在用户主动提供且职位表要求时使用 |
| 备考可用时间和考试日期 | 用于生成计划，不影响资格判断 |

敏感信息（身份证号、联系方式、精确住址等）不采集、不落库。

## 4. 核心流程

### 4.1 来源登记与岗位获取

来源采用白名单登记，至少记录 `source_name`、`url`、`publisher`、`region`、`source_type`、`last_checked_at`。优先级为：招录机关/人社部门官网 > 官方考试机构 > 学校官网转载。转载内容只能作为发现入口，最终结论需回链原始来源。

公办大专来源额外记录 `institution_id`、`institution_name`、`ownership=public`、`school_type=junior_college`、`city` 和 `official_domain`。只有名录中确认的公办院校才进入自动监控。

公告发现阶段必须先执行可配置的关键词过滤，默认排除“成绩公示”“工伤送达”“工伤认定”“行政处罚”“政策解读”“人事任免”等非招聘政务信息；“面试”“体检”“考察”“拟录用”“递补”等招聘流程词保留。排除词与招聘词同时出现时进入待复核，不得仅凭单个关键词直接删除详情；每次过滤需记录命中词和规则版本。

每条岗位记录保存：公告标题、职位代码、单位/职位、工作地点、招录人数、学历学位、专业要求、应届要求、基层经历、政治面貌、资格证书、户籍/性别/年龄限制、报名与考试时间、原文 URL、发布时间和抓取时间。无法确认的字段标记为 `unknown`，不填默认值。

### 4.2 资格过滤

过滤分为硬条件和软偏好：

1. 硬条件逐项比对，结果为 `符合`、`不符合` 或 `待核实`；
2. 任一硬条件不符合的岗位不进入推荐列表，但保留淘汰原因；
3. 待核实岗位单独列出，展示需要用户向招录机关确认的问题；
4. 地域、通勤、单位性质等仅作为排序偏好，不能伪装成资格结论；
5. 专业匹配展示“原文要求、标准化专业、匹配依据”，不以关键词命中作为最终法律判断。

### 4.3 岗位分析

对每个可报或待核实岗位输出：

- 竞争指标：招录人数、已知报名/缴费人数、竞争比及统计口径；
- 历史分数：进面分数线、年份、科目和数据来源；样本不足时明确显示“数据不足”；
- 用户匹配：资格匹配、地域偏好、工作内容理解成本；
- 风险：公告变更、数据过期、专业口径不清、样本偏差、竞争数据缺失等；
- 综合标签：`优先核实`、`可重点准备`、`谨慎选择`，而非“稳进/必上”。

综合排序仅用于辅助浏览，建议默认权重：硬条件通过 50%、地域偏好 20%、历史竞争数据质量 15%、岗位偏好 15%。权重应在报告中公开，且不能把缺失数据当作低竞争。

### 4.4 备考建议

根据公告中的考试科目、题型说明、考试日期和用户可用时间，生成阶段计划：基础、专项、套题复盘。每周计划包含学习时长、科目、可验收产出和调整条件。公告未提供题型时，只能给出通用准备建议并标注依据，不虚构题量或分值。

## 5. 输出契约

每次回答按以下顺序组织：

1. **条件确认**：列出已知条件、未知条件和关键假设；
2. **岗位结果**：表格展示职位代码、单位、地点、匹配结论、待核实项；
3. **分析与风险**：竞争数据、历史分数、数据日期、置信度和风险提示；
4. **行动建议**：建议核实的问题、关注的公告节点、备考下一步；
5. **来源**：每条事实附原始 URL、标题、发布日期/抓取日期。

事实、计算和推断必须分开标识。无来源的数字不得展示为事实；抓取失败时说明失败原因并请求用户提供链接或文件。

## 6. 数据与质量要求

- 使用统一日期、地区、专业和考试类型枚举；原文保留，标准化值可追溯；
- 竞争比必须注明“报名/缴费/最终参考”的分母和统计日期；
- 历史分数必须注明最低进面、平均分还是区间，禁止混用；
- 来源超过设定有效期（默认 7 天）或公告有更新时，提示重新核验；
- 解析结果需支持人工纠错，并记录纠错前后的原文片段；
- 访问频率遵守网站规则和 robots/公开接口政策，不绕过访问控制。

## 7. 验收标准

- 给定一份职位表和用户画像，能逐项说明每个岗位为何符合、不符合或待核实；
- 任何推荐岗位都能展开看到原始来源和抓取时间；
- 缺少报名或分数数据时，不生成虚假的竞争比/分数预测；
- 公告专业表述模糊时，输出核实问题而不是强行判定；
- 备考计划只引用公告确认的科目与时间，并能按用户每周时长调整；
- 对“保证上岸”“代报名”“绕过验证码”等请求明确拒绝并给出合规替代方案。

## 8. 后续版本（不纳入 MVP）

在 MVP 运行并验证数据质量后，再评估多省份扩展、用户历史记录、更多事业单位类别和经过脱敏授权的统计数据。每次扩展必须新增来源质量和隐私评审。
